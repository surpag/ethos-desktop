# P0-2 方案评审：一个 Workspace 只有一个权威根

**基线**：`1c4d39a`。**本文不含任何代码改动**，只做问题空间枚举与方案对比。
状态标签沿用 P0-2 核验清单：`[已实测]` / `[源码已确认]` / `[待验证]` / `[设计建议]`。

---

## 0. 判据（先定，否则方案会滑向"能跑就行"）

不是「三个入口都能写文件」，而是分**有效**与**失效**两种状态各说一句：

> **有效状态**（未绑定 / 绑定且目录存在）：对同一个**合法且在授权范围内**的虚拟路径 `/home/user/workspace/{id}/x`，任何消费者在任何时刻访问的是**同一片字节**。
>
> **失效状态**（绑定目录被删 / 改名 / 盘符掉线 / 无权限）：所有消费者**一致地拒绝访问**——不得自动创建空目录、不得回退到旧 Volume、不得用任何路径替代。绑定状态不因目录暂时不可用而退化成"未绑定"。

第二句是 2026-11-20 的修正。原判据写的是"三种状态下都必须看到同一片字节"，这在失效状态下不可能成立（真实目录已经不存在），于是判据本身就不可满足——一条无法满足的判据最终一定会被降级成"能跑就行"。拆成两态之后，失效状态有了可测的结论：**一致拒绝**。

两句都只覆盖**合法路径**，这不是措辞保守，而是事实边界（2026-11-20 追加）：

> 对**合法且处于工作区授权范围内**的路径，所有消费者访问同一权威根；对**非法路径**，各入口遵循**自身**的拒绝策略。当前 Shell 不具备与文件工具等价的工作区越界保护，**不得把路径映射描述为 Shell 安全隔离。**

原因是两侧能力根本不是一回事（§6.2 有完整对照表）：文件工具有虚拟路径范围检查 + 真实路径敏感检查，Shell 侧两项都没有，只有文本替换。所以"路径统一"绝不等于"权限统一"——这条要写在判据里，而不是留给读者推断。

配套硬约束（继承自 P0-1，不可让步）：**未绑定工作区的落点、越界判定、`workspace-volumes/{id}` 的物理位置一律不变。**

## 1. 状态空间枚举

三个维度组合出必须逐格定义的输入：

| 维度 | 取值 |
| --- | --- |
| 绑定状态 | 未绑定 / 绑定且目录存在 / 绑定且目录被删、改名、盘符掉线 |
| 旧数据 | volume 里有旧副本 / 没有 |
| 目录性质 | 普通目录 / 本身是 git 仓库 / 是另一个工作区的根（嵌套绑定） |
| 消费者 | 6 个文件工具 · shell · `git` · `git_push` · 文件面板 · 上传 · 敏感路径检查 · 输出归一化 · `destroy` |

3 × 2 × 3 × 9 = 162 格，但真正需要设计决策的只有 6 处，**已全部裁决**（§5）。**枚举的意义不在填满表格，而在于证明方案没有只对"绑定 + 目录存在 + 普通目录"这一格有效**——那正是当前实现唯一覆盖的格子。

已确认的三格：未绑定（全部一致，`[已实测]`）、绑定+目录存在（执行链一起偏离，`[已实测]`）、绑定+目录存在+git 仓库（同上，见核验清单 §9.1）。

**绑定目录被删这一格**已于 2026-11-20 核验（§7 第 1 项）；产品语义另在更早时点裁决为 **fail-closed**（§5 第 3 条）：所有消费者一致拒绝，不重建、不回退。裁决先于实测是刻意的——这一格不存在"看现状再决定"的空间，现状本身就是缺陷。**核验结果比原先假设更糟**：不存在任何 `FileExistsError` 路径，执行链对绑定结构性盲，会在 `workspace-volumes/{id}` 静默建空副本；面板本地路径解析为 `None` 时回落读该副本——即静默回退，而不是报错。

## 2. 决定性实测：`{id}` 不可能既是实体目录又指向用户目录

P0-2 原本最自然的想法是「把 `workspace-volumes/{id}` 换成指向 `local_root` 的目录联接」。本轮补测了三种挂法，结论是这条路不可用。**但措辞需要撤回一处**（2026-11-20 复核，见 §7 第 4 项）：不能写成"MSYS 无法进入 junction"——内容是可访问的，退化发生在**枚举视图**，不在访问本身。下表的判定列按此口径读。

| 挂法 | `ls -la <path>` | `find <path>`（无尾斜杠） | 判定 |
| --- | --- | --- | --- |
| **现状**：联接在 `{root}/workspace` → volumes，`{id}` 是实体目录 | 正常 | 正常递归 | ✅ P0-1 修的就是这个 |
| 联接在 `{root}/workspace/{id}`（单跳） | 只显示链接本身 | 只输出自身，`exit=0` | ❌ P0-1 已实测 |
| **两层联接**：`workspace` → volumes，`volumes/{id}` → 用户目录 | **只显示链接本身** | **只输出自身，`exit=0`** | ❌ 本轮新实测 |

两层联接的实测输出（`[已实测]`，临时目录，`mklink /J`）：

```
$ ls -la workspace/ws1
lrwxrwxrwx ... workspace/ws1 -> /c/.../twohop/user          ← 不进入
$ ls -la workspace/ws1/
total 1 ... pkg  seed.txt                                   ← 尾斜杠才进入
$ find workspace/ws1
workspace/ws1                                               ← 只有自身，exit=0
$ find workspace/ws1/
workspace/ws1/  workspace/ws1/pkg  workspace/ws1/pkg/main.py  workspace/ws1/seed.txt
$ cd workspace/ws1 && find .
.  ./pkg  ./pkg/main.py  ./seed.txt                          ← cd 之后正常
```

四点结论（第 1、2 条为 2026-11-20 复核实测后重写）：

1. **能访问，但枚举视图不一致。** 判定看的是"路径末端这一跳"：只要 `{id}` 本身是 junction，`ls -la` 就把它显示成链接、`find`（无尾斜杠）不下降；但 `ls -la <path>/`、`cat <path>/f`、`cd <path>` 全部正常（`[已实测]`，2026-11-20）。此前"MSYS 无法进入 junction"的说法**撤回**——它错在把"枚举不到内容"和"访问不到内容"混为一谈。
2. **`find` 不下降不是 MSYS 特有**：POSIX `find` 默认不跟随符号链接（要 `-L`）。判据应写成"**任何区分链接与目录的消费者**"，而不是"MSYS 的毛病"。原生 Windows 侧本轮补测结论相反：PowerShell 对 junction 完全正常（列目录、读穿、递归枚举、cwd 切换都进）；`cmd.exe` 受本机执行策略限制未能运行，保持未测。
3. 失败是**静默的**：`find` 不递归却返回 `exit=0`，模型看到的是"目录是空的/只有一项"，不会看到错误。
4. 唯一活路是调用方永远带尾斜杠或先 `cd`——而 `find work`、`ls work` 是模型最常用的写法。**把正确性寄托在模型的斜杠习惯上，等于没有约束。**

由此得到一条硬约束（本文最重要的结论）：

> **在现有的 POSIX 消费者语义（MSYS / Git Bash / `find`）与现有目录访问链路下，`{root}/workspace/{id}` 必须是实体目录。** 联接只能挂在它**之上**（现在的 `{root}/workspace`）。这不是"所有消费者都如此"的普适断言：原生 Windows API 与 PowerShell 会把 junction 当普通目录正常遍历（`[已实测]`）。约束按**最弱的那个消费者**定，不按最强的定——执行链里跑的是 POSIX shell，模型的探查命令也按 POSIX 语义解释。

而「让实体目录的内容等于用户目录」只有复制、硬链接、Windows 卷挂载点三条路：复制 = 回到双副本（否决）；硬链接只承接已存在文件、不承接新建与删除（否决）；卷挂载点要求目录为空且需管理员（否决）。

**所以：文件系统布局这一层无解，收敛点只能在"路径解析 + shell cwd"这一层。** 这也解释了为什么 P0-1 的联接方案对 `{root}/workspace` 有效、对 `{id}` 无效——它不是"联接不好用"，而是"联接挂错层级"。

## 3. 候选方案

### 方案 A：在 `volumes/{id}` 建联接 —— 否决

直接由 §2 否决。附带两个次级问题（都实测过，记录以免将来重提）：

- `shutil.rmtree` 作用在 junction 上**抛 `OSError: Cannot call rmtree on a symbolic link`**，而 `os.path.islink()` / `Path.is_symlink()` 对它返回 **False**。好处是目标目录绝不会被误删（`[已实测]`：`keep.txt`、`sub/a.txt` 全部完好）；坏处是任何基于 `rmtree` 的清理会失败而非降级。
- `destroy()` 对绑定工作区只解绑不删文件（`volume_backend.py:217-221`，`[源码已确认]`），联接头本身会残留，需要显式摘除——而"摘链接"和"删目录"在代码里必须继续走两套原语。

### 方案 B：单点映射（`resolve()` + shell cwd）—— 唯一不引入第二份内容的路径

- 文件工具：`resolve()` 是唯一决定点（核验清单 §2.1 已确认），返回 `local_root` 派生路径。
- shell：`_translate` / cwd 解析把 `/home/user/workspace/{id}/…` 映射到 `local_root/…`，**命令在用户目录里真实执行**。
- `git` / `git_push`：cwd 与 shell 同源，自动跟随，不需要独立分支。（2026-11-20 核验：`_op_git` → `commands.run(cwd=…)` → `resolve()` 确实共用同一决定点；但"**零代码改动**"取决于 S2 是否覆盖 `resolve()` 这一层，而不是覆盖 `files.*`——见 `docs/p0-2-preflight-verification.md`）
- 面板 / 上传：本来就指向 `local_root`，不变。

代价（必须在方案评审阶段就承认，不能留到实施时"发现"）：

1. **shell 输出会出现宿主绝对路径**，`pwd` 直接打印 `C:/Users/…`。约束 4（输出归一化）从"P0-4 可选项"变成**P0-2 的必需项**。
2. `_normalize` 是**文本替换**（`local.py:946`），处理不了大小写变更、8.3 短名、转义、base64。它是**呈现层过滤器，不是安全边界**——这条必须写进文档，否则下一个人会拿它当隔离依据。
3. `_path_pairs()` 目前只知道 sandbox 根（`local.py:965`），不知道"当前是哪个工作区"。要归一新根，就得把工作区上下文传进 shell 层 → **结构性依赖 P0-3 的注入点**，不能本阶段偷偷塞一个全局变量。
4. shell 看不到"未绑定卷"和"绑定目录"之外的任何东西这件事没有变——shell 本来就没有边界（`unrestricted`），方案 B 不新增暴露面，也不提供隔离。

#### 3.1 必测项：shell 的三种路径形态（已实测，结论比预想更严重）

只改 cwd 是不够的——**cwd 与命令里的路径不是一回事**。绑定态下实测（临时 `ETHOS_DATA_DIR`，绑定目录只含 `seed.txt`）：

| # | 命令 | 落点 |
| --- | --- | --- |
| 1 | `pwd`（cwd = `/home/user/workspace/ws-bound`） | 打印 `/home/user/workspace/ws-bound` |
| 2 | `echo rel > rel.txt`（相对路径） | **volume**（绑定目录 `False`） |
| 3 | `echo virt > /home/user/workspace/ws-bound/virt.txt`（虚拟绝对） | **volume** |
| 4 | `ls -la /home/user/workspace/ws-bound` | 列出 volume 里的 `rel.txt` / `virt.txt` |
| 5 | `cd /home/user/workspace/ws-bound && pwd` | 仍是虚拟路径 |
| 6 | `echo host > '<宿主绝对路径>/host.txt'` | **绑定目录**（shell 直接走真实路径，不需要翻译） |
| 7 | 默认 cwd | `/home/user/work`（不是工作区根，属 P0-3） |

落点核对：`rel.txt`、`virt.txt` → volume 有、绑定目录没有；`host.txt`、`seed.txt` → 绑定目录有、volume 没有。

两点结论：

1. **虚拟绝对路径必然经 `_translate` → 挂载 → volume**。方案 B 如果只把 cwd 换成 `local_root`，那么"相对路径写用户目录、虚拟绝对路径写 volume"——**同一轮对话里就分裂**，而且比现在更难排查（模型以为自己一直在工作区里）。
2. `pwd` 打印的是虚拟路径，说明 `_normalize` 正在把 `workspace-volumes/{id}` 反向替换成 `/home/user/workspace`（`local.py:968-970` 的 pairs）。换根之后，这套替换必须**同时**覆盖 `local_root`，且需要知道"当前是哪个工作区"——否则 `pwd` 会直接打印宿主路径。

所以方案 B 的正确表述不是"映射 cwd"，而是：

> **`resolve()`（文件工具）与 `_translate()`（shell 命令文本 + cwd）必须由同一份「虚拟路径 → 权威根」映射驱动；任何一处独立维护映射，都会重新制造分裂。**

`resolve()` 与 `_translate()` 现在是两段各写各的逻辑（一个返回 `Path`，一个做正则替换），这正是 P0-2 要收敛的那一处。文件工具走前者的前提是它已经统一过了；shell 侧后者的统一必须同批完成，否则等于只修了一半。

"同一份映射驱动"不等于"两边调用同一个函数"——两者的输入形态不同（完整路径 vs 命令文本），强行合并会毁掉文本替换必须保持的保守性。这条边界的精确表述见 §6.1，含文本层的已知极限（拼出来的路径覆盖不到）。

顺带一条安全要求：映射改变后，越界与敏感检查必须针对**映射后的真实路径**判，而不是虚拟路径。§6.2 已逐条核对：三道敏感检查里有两道本来就是 `realpath(resolve(...))`，换根后自动跟随；`_scope_violation` 是虚拟层的授权卡点，与换根正交、依然有效。


### 方案 C：给每个工作区一个独立沙箱根 —— 否决

在 `{root}` 下为每个工作区建独立根、把 `workspace/{id}` 变成 `{root}` 本身，等于"每个工作区一个沙箱"。它没有解决 §2 的问题（仍然是联接或复制二选一），却把会话与工作区的绑定关系、`skills` 挂载、`/home/user` 语义全部推翻。**代价远超收益，且违反"最小改动"。**

### 方案 D：文件工具与 shell 各走各的（保持现状 + 只修文档）—— 否决

即承认"两条链"，靠 prompt 告诉模型"文件工具看到的是 A，shell 看到的是 B"。这直接违背 P0-1 建立的不变量，且实测已经证明模型会陷入"写完就 ls 不到"的重试循环（21 次调用里 15 次找同一个文件）。

**结论（`[设计建议]`）**：只有方案 B 同时满足 §0 的判据与 §1 的硬约束。它不是"最好的方案"，是排除法剩下的唯一方案。

## 4. 四个约束在方案 B 下如何同时成立

| 约束 | 在方案 B 下的落点 | 剩余风险 |
| --- | --- | --- |
| ① 绑定已有 Git 仓库 | `git` 的 cwd 与 shell 同源 → 自动看到真实仓库。**但** `.git` 是 `permissions/paths.py` 的固定敏感段（所有档位都拦），文件工具读它永久不可用；历史只能经 `git` 工具拿。另外 `git add` 只接受显式路径（`git add .` 在参数层被拒） | 「Agent 能不能理解一个已有仓库」完全取决于 `git` 工具的表达力（`status`/`log`/`diff`/`show` 够不够）；要支持 `add .` 必须单独放宽白名单，且依赖 `plan_git_add` 按条目判定 |
| ② 旧 Volume 数据 | **已裁决（2026-11-19）**：保留在原位置，不自动合并、不自动删除；绑定成功后旧 Volume **不再作为当前工作区的活动数据源**。`merge_existing` 保持"用户显式勾选才合并"，恢复/迁移作为独立流程（先预览冲突再执行） | 需要把「活动工作区 / 历史数据」两个概念写进 UI 与文档，否则用户看到 volume 里还有文件会以为丢了或以为还在用 |
| ③ `.git` 权限规则 | **已裁决：不改**。它是不可配置层，与"谁是权威根"正交 | 需要在文档与工具描述里写明：读 `.git` 被拒不是 bug；同时确认拒绝文案不会让模型以为是"路径错" |
| ④ 路径输出归一化 | 方案 B 的必需项，且需要工作区上下文（依赖 P0-3 的注入点）。**已裁决**：接受有限宿主路径暴露；常见形态应归一（`pwd`、命令输出、错误信息），归一失败不得影响命令执行与实际结果；归一必须用**当前工作区上下文**，不得全局替换把别的工作区路径改错 | `_normalize` 只是文本过滤；8.3 短名 / 大小写 / 转义形态会漏。**不能宣称"已消除宿主路径暴露"**；归一化是呈现层体验优化，**不是安全承诺** |

四条约束之间**没有真正的冲突**：③ 是正交的（换不换根都拦），① 由 cwd 同源自动满足，④ 是方案 B 的必付成本，② 已裁决为"保留旧 Volume、不合并、不作活动数据源"。原来唯一的结构性冲突（② 与"最小改动"）用**产品决策**消掉了：不迁移就不需要动用户目录，代价只是"旧 volume 内容不再被任何消费者看见"，而这一点已被显式承认并写入概念区分（活动工作区 / 历史数据）。

剩下的风险全部集中在 ④，且它不是"成本"而是**方案 B 的一部分**：§3.1 已证明 `_translate` 必须与 `resolve()` 共用解析器，否则换根只换了半边。

五项裁决全部落地后，矩阵的形态变了：**没有一条约束还停留在"待定"**。③④ 是"接受现状 + 明确表述边界"，①② 是产品决策，唯一剩下的不确定性是**实现是否真的做到**——那由 §6 的三个审查问题回答。

## 5. 裁决记录（逐项，2026-11-19 / 11-20）

> 裁决只记录结论，不改写理由。已裁决的条目保留原文，避免后来者以为问题从未存在。

1. **（已裁决 2026-11-20：接受有限暴露；归一化属呈现层优化，不是安全承诺）shell 输出暴露宿主路径，可接受吗？** 方案 B 下 `pwd` 必然是宿主路径，`_normalize` 只能覆盖常见形态。裁决表述为"呈现层尽量归一，不承诺完全消除"。

   附加两条硬要求：① 常见形态必须归一——`pwd`、命令输出中的路径、**错误信息中的路径**；② 归一化失败（替换抛错、编码异常）不得影响命令执行，也不得改变命令的实际结果——它是后处理，不是流水线的一环。③ 归一必须使用**当前工作区上下文**，禁止全局替换把别的工作区的路径改错（§3.1 的 `_path_pairs` 现在只有 sandbox 根，没有工作区维度）。

   裁决理由（用户给出）：执行位置本来就是用户指定的宿主目录，`pwd` 天然可能输出宿主路径；`_normalize` 是文本处理不是安全边界；shell 当前本来 unrestricted，模型可以通过命令访问宿主路径——不能把输出归一化包装成隔离能力。

2. **（已裁决 2026-11-19：保留，不自动合并、不自动删除、不作活动数据源）旧 volume 内容默认怎么处置？** 四个候选：丢弃 / 自动合并 / 保留但不可见 / 迁到 `legacy/` 子目录。原判据是"这一条不定，实施时必然临时发明一个"。

   裁决理由（用户给出）：自动合并有覆盖风险（用户目录可能已有同名文件，尤其代码仓库、配置与 `.git`）；直接丢弃不可接受（可能是用户此前让 Agent 生成的代码）；迁到 `legacy/` 会修改用户目录，还要处理冲突、权限、软链接与 Git 仓库。

   | 场景 | 处理 |
   | --- | --- |
   | 首次绑定已有工作区 | 保留旧 Volume，不自动合并 |
   | 绑定后继续使用 | 只操作用户绑定目录 |
   | 用户取消绑定 | 不自动删除旧 Volume |
   | 用户需要旧数据 | 后续提供显式的恢复 / 迁移能力 |
   | 用户主动要求合并 | 独立迁移流程：先预览冲突，再执行 |

   两个概念要进 UI 与文档：**活动工作区**（Agent 当前真正读写）与**历史数据**（旧 Volume，不参与解析）。UI 必须明确区分，否则用户看到旧 Volume 里还有文件，会以为数据丢了或以为绑定失败。
3. **（已裁决 2026-11-20：fail-closed，禁止重建与回退）绑定目录被删/改名/盘符掉线时怎么办？**

   | 状态 | 行为 |
   | --- | --- |
   | 未绑定 | 继续使用原来的 Volume 根 |
   | 已绑定且目录存在 | 使用绑定目录 |
   | 已绑定但目录被删 | 报错，拒绝执行 |
   | 已绑定但目录被改名 | 报错，拒绝执行 |
   | 已绑定但盘符掉线 | 报错，拒绝执行 |
   | 已绑定但无访问权限 | 报错，拒绝执行（原因与上面区分） |
   | 用户主动解绑 | 按明确的解绑流程处理 |

   **不保留"重建空目录"作为候选。** 理由（用户给出）：Agent 已在绑定目录里写了 `src/main.py`，盘一掉线就自动建空目录甚至回退旧 Volume，结果是"项目突然没有文件 → 模型在错误位置重建项目 → 用户恢复磁盘后出现两个内容不同的工作区"。这与 P0-2 要解决的问题完全相反。

   两条附带要求：① **绑定状态不能因目录暂时不可用而自动变成未绑定状态**；② 报错必须区分「目录不存在」「无权限」「磁盘不可用」，不得统一包装成"工作区为空"——后者正是核验清单 F 系列里那类"把故障压成空"的老毛病。

   现状（`[已核验 2026-11-20]`，原假设作废）：**不存在 `FileExistsError` 路径**。当前不是"会报错但报得难看"，而是**根本不报错**——① `_workspace_volume_dir` 对 `workspace-volumes/{id}` 无条件 `mkdir(exist_ok=True)`（`local.py:731`），绑定目录缺失时执行链就在该空副本上继续读写；② 面板 `local_workspace_path` 拿不到本地目录时返回 `None`，`http.py:85-88` 随即**回落读沙箱副本**，用户看到的是旧 Volume 内容；③ `http.py:95-97` 把列目录异常吞成空列表。

   所以这一格不是"加一个异常判断"能收口的：要接线（S2）、要去回落（S3）、要去掉两处无条件 mkdir（`local.py:731` 与 `local.py:901`——`commands.run` 在 `resolve()` 之后又 mkdir 了一次，只改前者会被它绕过）。
4. **（已裁决 2026-11-20：暂不放宽）`git add` 是否接受 `.`？** 维持显式路径白名单：`git add src/main.py` 允许，`git add .` 拒绝。

   理由（用户给出）：不是 `git add .` 一定不安全，而是它**改变了授权粒度**——现在是对模型给出的具体条目逐条判权限，`.` 会把当前目录下所有可暂存内容一次性纳入（`.env`、新文件、删除、符号链接）。即使 `plan_git_add` 有按条目判定能力，也不在 P0-2 顺手扩大授权范围。

   将来若支持，前置条件写死：必须先**枚举实际暂存集合**，再逐条执行权限检查——不能只检查 `.` 这个目录本身。
5. **（已裁决 2026-11-20：必须注入，且按调用传递）是否允许把工作区上下文注入 shell 层？** 不注入则约束 ④ 无法实现（§3.1 已证明），所以这不是架构偏好。

   注入形态裁决：**单次执行上下文，不引入共享可变状态。**

   ```
   await commands.run(command=..., cwd=..., workspace_context=ctx)
   ```

   （仅为接口方向示意，不是实施指令。）禁止的写法是 `commands.current_workspace = ws_a` 这类可被不同会话反复改写的实例状态——ETHOS 是多用户多会话服务，可变共享状态迟早串工作区。

   原则四条：工作区上下文由调用方明确传入；单次执行只用本次的上下文；不依赖全局变量或可变共享状态；文件工具与 Shell 使用**同一个权威根目录来源**（越界拒绝只由文件工具侧的 `resolve()` 执行，Shell 不具备等价能力，见 §6.2）。
6. **（已裁决 2026-11-20：接受并扩大为四组）验收判据用哪一组测试？**

   | 组 | 内容 |
   | --- | --- |
   | 一、绑定态路径一致性 | 文件工具读写绑定目录；Shell 三形态；Git `status`/`log`/`diff`/`commit` 操作绑定仓库。要求同一虚拟路径的所有消费者看到相同内容 |
   | 二、Shell 三形态回归 | 固化 §3.1 的七条命令，特别是 `echo relative` / `echo virtual > /home/user/workspace/{id}/...` / `echo host > '<host-root>/...'` 三个文件必须落到同一权威目录 |
   | 三、异常状态 | 绑定目录删除 / 改名 / 盘符不可用 / 无访问权限 / 本身是 git 仓库 / 含符号链接或 junction / 旧 Volume 有数据。**异常情况必须 fail-closed，不得回退或重建** |
   | 四、未绑定态反向断言 | 未绑定工作区仍用 `data_root/workspace-volumes/{id}`；物理位置、路径解析、越界判定、三入口行为全部不退化 |

   第四组是本轮新增的强制项：它是唯一能证明"换根没有把未绑定态一起改掉"的断言。测试环境条件必须写明：**默认未配置 `EDITH_WORKSPACE_VOLUME_DIR`**——否则连未绑定态都是分裂的（核验清单 F-5）。

## 6. 最终设计审查：三个问题的答案

裁决齐了，但方向批准不等于实现可达。以下三个问题是"方案 B 是否真能落地"的闸门，逐条给源码依据。

### 6.1 `resolve()` 与 `_translate()` 能共用"一个解析器"吗？——能，但"共用"必须精确定义

先看两者现在各是什么（`[源码已确认]`）：

| | `resolve(virtual) -> Path`（`local.py:566`） | `_translate(cmd) -> str`（`local.py:977`） |
| --- | --- | --- |
| 输入 | **一条完整路径** | **整条命令文本** |
| 做什么 | 前缀分流 `workspace/{id}` / `skills` / 沙箱根；`normpath` 后做 `..` 与 `is_relative_to` 越界判定 | `_VIRTUAL_ROOT_RE.sub` 把 `/home/user` 整段替换成 `self._sb.root` 的 shell 写法 |
| 是否知道工作区 | 知道（`workspace/{id}` 那一段） | **不知道**——它只认 `/home/user` 这个固定前缀，之后全靠 `{root}/workspace` 联接链落到 volumes |
| 是否做越界检查 | 做 | **不做**，也不可能做（输出是字符串，不是路径） |

所以"共用"不能是字面意义的"两者都调用同一个函数"，也不能是"两者遵守同一条越界规则"。精确的共用内容是一份数据加一层分工：

1. **共享映射数据**：`(虚拟前缀 → 权威根)`。绑定态下 `/home/user/workspace/{id}` → `local_root`，未绑定态下 → `workspace-volumes/{id}`。这份数据由同一个来源生成（`local_root_of(workspace_id)` 或它的空值分支），不允许多头维护。
2. **路径策略分层**：文件工具通过 `resolve()` 执行路径归一化与越界拒绝；Shell 只负责明确虚拟路径前缀的文本替换和 cwd 映射，**不具备等价的越界拒绝能力**，不得宣称它执行了同一条越界规则。依据是 §6.2：`cd {root}/../../..` 会离开绑定目录且不经过任何检查——若文档写成"Shell 不得破坏越界规则"，实际含义就变成"Shell 至少能保证不逃出工作区"，而那正是它做不到的事。

**为什么不能让 `_translate` 直接调用 `resolve()`**：`_translate` 面对的是任意命令文本。若让它去解析整条命令的 token 再逐个 `resolve`，它就开始对 `echo "a/b"`、`grep 'x/y'`、heredoc 这类字符串动手——比现在的 bug 更糟。所以它必须保持"只替换明确前缀"的保守策略。

于是这里有一条**必须写进文档的极限**：

> `_translate` 能保证「命令里写出来的虚拟绝对路径」与 cwd 同源；**不能**保证「拼出来的路径」同源——`$WS/src`、`$(pwd)/x`、`cd ..` 之后的相对操作都覆盖不到。

**这类动态路径行为不属于文本替换器能够保证的范围**，因此有两条硬规定：

1. 验收文档不得把它们列为"已实现的路径一致性能力"。第一组 / 第二组测试只断言**字面路径**（相对 / 虚拟绝对 / 宿主绝对三种固定写法），不得把变量拼接算进覆盖。
2. 它们不是"以后加强正则就能解决"的问题——文本层拿不到命令的运行期语义。要么接受为已知缺陷（写进用户可见的边界说明），要么等到命令在真实进程里执行、由 OS 侧约束（那是 OS 级隔离，独立立项）。

补足手段不是加强正则，而是另外两条：cwd 用真实路径（相对路径天然同源，这解决了绝大多数写法）+ 输出归一化（只处理呈现）。**承认极限比假装覆盖更安全**：只要文档写着"文本层只覆盖字面路径"，后续排查就不会误以为已经全覆盖。

结论：**能共用，但共用的是映射数据与权威根目录来源，不是同一个函数；越界规则由文件工具执行，Shell 不具备对应的执行能力。** 这条定义要写进实施方案，否则实施时很容易做成一个 `_map()` 被两边调用，然后在 `_translate` 里把正则替换能力弄丢。

### 6.2 映射后的真实路径还受越界/敏感检查保护吗？——文件工具侧：**是**；Shell 侧：**不适用**

`[源码已确认]`，`tools.py` 的敏感检查是三道：

| 遍次 | 函数 | 判什么 | 换根后 |
| --- | --- | --- | --- |
| 一 | `_sensitive_path_violation`（:164） | 逻辑路径字符串 | 正交，不变 |
| 二 | `_sensitive_real_violation`（:180） | **`os.path.realpath(sandbox.resolve(virtual))`** | **自动跟随**：`resolve` 换根 → `realpath` 落到 `local_root` → 判的正是真实落点 |
| 三 | `_sensitive_subtree_violation`（:257） | 同上，再 `first_sensitive_entry(real)` 按条目展开（仅 `delete`） | 同上，自动跟随 |

授权层 `_scope_violation`（:138）只用 `workspace_path(..., current_workspace_id=...)` 判虚拟前缀——它是**授权**卡点，与换根正交，换根后依然有效，也依然不能替代真实路径检查（两者职责不同，不要合并）。

但"文件工具有三道检查"不等于"所有消费者都有"。这张表必须写在文档里，否则下一次讨论一定会把"路径统一"当成"权限统一"：

| 能力 | 文件工具 | Shell（`run_command`） |
| --- | --- | --- |
| 虚拟路径范围检查 | **有**（`_scope_violation` + `resolve()` 上溯拒绝） | **无** |
| 真实路径敏感检查 | **有**（第二 / 三遍 `realpath(resolve(...))`） | **无** |
| 工作区根映射 | 需要统一（`resolve()` 是唯一决定点） | 需要统一（`_translate` + cwd） |
| 越界路径拒绝 | 工具层执行 | **不能由当前文本替换器保证** |

具体到这条命令：

```
cd /home/user/workspace/ws1/../../../
```

`_translate` 会把前缀替换成 `local_root`，剩下 `../../..` 交给 shell 自己解析——**最终离开绑定目录，而且不经过任何检查**。文件工具对同一路径会直接拒（`resolve()` 的 `..` 上溯判定），所以两侧必然不对称。

**所以：换根绕过检查这条路，在文件工具侧是堵住的；在 Shell 侧从来没有这道门。** 这不是本轮引入的缺口（Shell 本来就 `unrestricted`），但它决定了 §0 判据只能覆盖合法路径。剩下的记录：两条缺口 + 一条明确不做。

1. **绑定目录本身位于敏感路径下**：若绑定到 `~/.ssh` 这类目录，该目录下**所有**文件的真实路径都含敏感段 → 整个工作区全拒；若绑定到家目录，则只有走进 `.ssh` / `.env` 等敏感段时被拒（与未绑定态行为一致）。前者是 fail-closed，**判断正确但需要文案**，否则用户会以为绑定失败。列入异常状态测试组。
2. `files.remove` 的 `_is_link(real)` 守卫（`local.py:848`）在换根后仍然生效：绑定目录里的 junction 不会被 `rmtree` 顺着删掉。这条是 P0-1 留下的，换根不影响。
3. **不做的事**：不给 Shell 补越界检查。那需要把"命令文本 → 实际访问的每个路径"解析出来，是 OS 级隔离（Job Object / 容器 / 审计钩子）的题目，属独立立项；在文本层伪造这道能力只会制造"以为隔离了"的假象。

### 6.3 上下文注入会影响多用户/多会话并发吗？——按调用传递；"当前无共享实例"≠"并发风险为零"

`[源码已确认]`：

- `Service.workspace()` 每次调用都 `LocalSandbox.open(...)`（`service.py:109`），**不复用实例**；`LocalCommands` / `LocalFiles` 随实例构造（`local.py:518-519`）。所以"跨请求共享一个 commands 对象"这件事在当前这条调用链上不存在。
- 但"不存在"不等于"可以依赖"：如果上层在同一 run 内复用实例并并行发起多个工具调用，或者实例生命周期跨越工作区绑定关系变化（`service.py:102-104` 的注释明写"会话可以换绑工作区"），那么实例级可变状态和缓存可能产生竞争或残留旧值；这两类情况尚未完成验证，不能当成当前已发生的问题。

**这条源码事实只能证明一件事**：当前调用链没有复用同一个 `LocalSandbox` 实例。它**不能**证明整个系统并发风险为零。以下四项本阶段**没有验证**，不得当成已排除：

| 未证明项 | 为什么它不在"已证"范围内 |
| --- | --- |
| 同一个 workspace 是否可能被多个会话同时执行 | 本次只看了 `Service.workspace()` 的实例创建，没查工作区级的并发准入 |
| 绑定关系是否可能在一次执行期间变化 | 会话可换绑（上引注释），但"执行中换绑时在跑的 run 怎么算"未查 |
| 工作区根是否会在实例创建后被重新读取 | `load_and_bind_local_root` 有 `_local_root_loaded` 幂等守卫，但守卫的作用域是实例还是进程，取决于谁持有实例——本次未追 |
| `workspace_context` 是否会被不同异步任务共享或修改 | 这是**将来**的代码，现在没有；风险取决于注入形态（见下） |

> 2026-11-20 更新：前两项与第三项已在 §7 第 5 项核验（同 workspace 多会话进程内已互斥；执行中换绑的漂移窗口真实存在；`_local_root_loaded` 是进程级守卫）。**仍未覆盖的是多进程 / 多副本场景**——进程内 dict 失效的那一天，这三条结论一起失效。

所以正确的结论是有限定的：

> 当前调用链每次通过 `Service.workspace()` 创建独立的 `LocalSandbox` 实例，**未发现依赖共享实例级 workspace 状态的路径**；但这不构成"整个系统并发风险为零"的证明。

实施时的补偿要求：**单次调用上下文 + 执行开始时固定 workspace id 与权威根目录**——一次执行内不允许因为绑定关系变化而让路径语义漂移（哪怕实例是新的）。三条落地要求：

1. **注入点现在断在 tools 层**：`execute(...)` 有 `workspace_id`（`tools.py:504`），但 `_op_sandbox_run_command` 的签名是 `(self, sandbox, args)`（`tools.py:836`）——**拿不到 workspace_id**，且它把 cwd 硬编码成 `WORKSPACE.work_path()`（`/home/user/work`，不是工作区根）。这两处是 P0-3 的具体改动位置，P0-2 只记录不改。
2. 禁止模块级/实例级 `current_workspace`。`ContextVar` 可用（作用域随 task），但最稳仍是显式参数——参数传错是编译期就能发现的错误，ContextVar 传错只在运行期表现为"偶发串工作区"。若用 `ContextVar`，必须在执行入口 set 一次、执行结束不残留（token 作用域），不得靠"下一次覆盖"。
3. 顺带发现（**不改，另立项**）：`_background` 挂在 sandbox 实例上（`local.py:522`），实例每次新建 → 跨请求 `commands.list()` 必然为空、后台进程无法被后续请求 kill。这是**既有问题**，与换根无关，不纳入 P0-2 修复范围；但"按调用传递上下文"会碰到同一个位置，实施时要小心别把它当成本轮引入的回归。

### 6.4 三个问题的结论

| 问题 | 结论 | 附带条件 |
| --- | --- | --- |
| ① 共用"解析器" | **可以**（仅指映射数据与 cwd 映射） | 共用的是映射数据与权威根目录来源，不是同一个函数；越界规则由文件工具执行，Shell 不具备对应的执行能力；**动态路径（`$WS/x`、`$(pwd)/x`、`cd ..`）不在保证范围**，验收不得列为已实现能力 |
| ② 换根后检查是否仍生效 | **文件工具侧：是**；Shell 侧：**不适用**（本来就没有） | 二、三遍已走 `realpath(resolve(...))`，自动跟随；需补"绑定到敏感目录"用例与文案；**不得把路径映射描述为 Shell 安全隔离** |
| ③ 并发影响 | **未发现依赖共享实例级 workspace 状态的路径**，但这**不等于**整个系统并发风险为零 | 三项已于 §7 核验（含"执行中换绑存在漂移窗口"），**多进程/多副本仍未覆盖**；实施时按调用传上下文，并在执行开始时固定 workspace id 与权威根 |

冻结的边界说清楚：**冻结的是"方向 + 边界"，不是"实现无风险"。** 方案 B 不再新增候选，后续改动只按本节条件收窄；本节标为"未验证"的四项不会因为评审通过就变成已验证——它们进 §7 或实施阶段的验收清单。
