## 0. 一句话结论

之前把 P0-2 理解成"两个目录映射错了"，这是不准的。

> **准确说法：绑定状态从来没有进入 Agent 执行链的决策过程。**

依据（`[源码已确认]`）：

| 事实 | 位置 |
| --- | --- |
| 全仓只有两处建联接：`{root}/skills`、`{root}/workspace` | `sandbox/local.py:679`、`:715` |
| `workspace-volumes/{id}` **从不**建联接 | 全仓 `_ensure_mount` 调用点仅上述两处 |
| 绑定只写进程内 dict，不落盘、不建链接 | `workspace/volume_backend.py:109-126` |

所以执行链不是"走了另一个根"，而是**根本没有第二个输入**。P0-2 要修的是"把绑定状态接进决策过程"，不是"把两个路径对齐"。

## 1. S1 前置：执行上下文快照

### 1.1 为什么必须快照，不能每次工具调用现查

| 事实 | 位置 |
| --- | --- |
| 绑定表是进程级可变 dict，且 `_dir()` 每次实时读 | `volume_backend.py:160-162` |
| `WorkspaceVolumeService` 是进程单例 | `main.py:154` |

不加速照就会出现：

```
Run 开始（ws=A）→ 工具 1 写 A → 用户换绑 ws=B → 工具 2 写 B → 同一 run 操作了两个工作区
```

**结论**：工作区上下文是"一次执行的快照"，不是"每次调用的动态查询"。这是 S1 的硬要求，不是优化。

### 1.2 两层职责必须分开（"纯函数"不能承担 I/O）

上一轮方案写的是"新增纯函数状态机"，这不准确：纯函数判不出目录是否存在、是否有权限、盘是否掉线。

| 层 | 职责 | 输入 | 输出 | 是否做 I/O |
| --- | --- | --- | --- | --- |
| 探测层 | 只报客观事实，不做业务判断 | 绑定记录 + 目标路径 | 存在性 / 是否目录 / 错误类别 | 是 |
| 解析层 | 合并事实与绑定信息 → 统一状态 | 绑定记录 + 探测结果 | 状态枚举 | 否（纯函数） |

状态枚举（5 个，**不设第六态**）：

| 状态 | 含义 | 与"从未绑定"是否同构 |
| --- | --- | --- |
| `UNBOUND` | 无绑定记录 | — |
| `BOUND_READY` | 有绑定且可访问 | 否 |
| `BOUND_MISSING` | 有绑定，目录不存在 | 否 |
| `BOUND_DENIED` | 有绑定，无访问权限 | 否 |
| `BOUND_OFFLINE` | 有绑定，设备/网络路径不可用 | 否 |

**不设 `DETACHED`**：解绑后对所有路径消费者的行为与"从未绑定"完全相同（都回 `volumes/{id}`）。差异只属于审计与历史记录，不该让路径解析器承担。若将来需要区分，扩的是绑定记录，不是状态机。

### 1.3 快照的边界条件

| 约束 | 要求 |
| --- | --- |
| 生成时机 | run 准入通过后、第一次工具调用之前，生成一次 |
| 快照内容（概念，非数据结构规定） | `workspace_id`、`binding_state`、`workspace_root`、`captured_at` |
| 使用方式 | 后续每次工具调用只读快照，不再查 `_local_roots` |
| 运行中换绑 | 不改变当前 run；只影响新 run |
| 快照态为异常 `BOUND_*` | 当前 run fail-closed，**禁止切回 `volumes/{id}`** |
| 快照态为 `UNBOUND` | 与今天逐字节相同（S1 的验收底线） |

### 1.4 固定根 ≠ 固定文件系统对象：必须按**时序**分三段

快照固定的是**路径字符串**，不是 inode。而"路径失效"发生在快照之前还是之后，处置完全不同——不能合并成一句"由 `BOUND_MISSING` 覆盖"（那是**快照前**才会出现的状态，快照后不会自己跳过去）。

| 时序 | 快照态 | 处置 | 明确不得做 |
| --- | --- | --- | --- |
| ① **快照前**目录已不存在 / 不可访问 | 探测得到 `BOUND_MISSING` / `BOUND_DENIED` / `BOUND_OFFLINE` | 准入后立即失败，**不进入工具循环**，不创建任何目录 | 不得降级成 `UNBOUND` 继续跑 |
| ② **快照后**（执行期间）目录被删 / 改名 / 盘掉线 | 快照**仍是** `BOUND_READY`（快照不可变） | 首次 I/O 失败即**当前 run 失败**；错误如实上报，具体是 missing / denied / offline 由 OS 错误码或一次补探测判定 | 不得改判快照状态；**不得回退 `volumes/{id}`**；**不得重建目录** |
| ③ **快照后目录又恢复** | 同 ②，该 run 已失败 | 不做特殊处理，下次 run 重新探测 | 不得自动重试当前 run |

**为什么 ② 里"不得跳状态"是关键**：快照的语义是"这次执行认定哪个根"。一旦允许运行中改判，就等于允许路径语义在 run 内漂移——那正是 P0-2 要消除的东西。所以 ② 的正确产物是**一次失败**，不是一个新状态。

**② 的具体陷阱（已核验，见 §2）**：`LocalCommands.run` 在 `resolve()` 之后无条件 `mkdir(parents=True, exist_ok=True)`（`local.py:901`）。绑定根在执行期间被改名后，这一行会**在原路径重建一个空目录**——不是回退 Volume，但同样是"凭空造出空目录"，用户把原目录恢复回来就会看到两处内容不同。因此契约必须包含一条：**绑定态下执行链不得对权威根及其 cwd 做 mkdir；cwd 必须已存在，否则报错。**

**这条规则不能推广到未绑定态**：未绑定态下 `volumes/{id}` 的按需创建是**工作区初始化**，今天必须保留（S6 第四组"未绑定态不退化"就是守它）。被禁止的是"在**用户提供的**权威根上创建或重建"。同一句"不要 mkdir"套到两个状态上，会直接把未绑定工作区废掉——这正是状态机存在的意义。

两条例外不在这张表里：

| 情况 | 处置 | 理由 |
| --- | --- | --- |
| 同一路径上目录被替换成另一个目录（内容变了、路径没变） | 按快照继续，不额外校验 | 路径语义未变；P0-2 只保证"语义不漂移" |
| 盘符重挂到另一台设备（路径没变、设备变了） | **不做**，记为已知未覆盖 | 路径层无法区分设备身份，属于 OS 级约束 |

**P0-2 不解"设备身份"，只解"路径语义不漂移"**。这条边界写在这里，是为了防止实施时被要求顺手解决设备级问题。

## 2. S5 前置：Git 的路径来源（已核验，不是假设）

上一轮写的是"Git 本是同一 `resolve()`，零代码改动"。这句话方向对、结论下得太早。实际调用链：

```
_op_git                      tools.py:908
  → root = WORKSPACE.workspace_path(id)     :921   ← 虚拟路径字符串
  → run_git(sandbox, root, ...)             gitops/executor.py:20
  → sandbox.commands.run(cmd, cwd=root)     executor.py:51
  → LocalCommands.run
  → work_dir = self._sb.resolve(cwd)        sandbox/local.py:900
  → work_dir.mkdir(parents=True, exist_ok=True)   :901   ← 第二个 mkdir
```

结论三条：

1. Git **确实**与文件工具共用同一个 `resolve()`，但经由 `commands.run` 这一层，不是 `files.*`。
2. 所以"零代码改动"是**有条件的**：条件 = **S2 覆盖到 `resolve()` 这个决定点**，而不是覆盖 `files.*`。S2 若只改 `files.*` 的入口，Git 不会跟随。
3. **`local.py:901` 是第二个无条件 mkdir。** S2 若只处理 `:731`，"不创建空目录"的验收断言会被这一行绕过。

`git_push` 单独一条：

| 段 | 是否经过 `resolve()` | 绑定态下的验收要求 |
| --- | --- | --- |
| 沙箱内 `git bundle create` | 是（同 `commands.run`） | bundle 必须生成在 `local_root` 内 |
| 后端带凭据 push | 否（不碰沙箱路径） | 与 P0-2 无关 |

**S5 的写法改为**：先验证 Git 工作目录与文件工具同源；若 S2 已覆盖 Git 的实际路径来源，则无需改 Git 代码，否则单独修正 Git 路径入口。**测试可以提前写，是否零改动由调用链决定。**

## 3. `workspace_id` 全局唯一性（已核验）

`_local_root_loaded` 只按 `workspace_id` 分键（`volume_service.py:37`、`:73-75`），看起来像跨用户串扰。实际不是：

| 事实 | 位置 |
| --- | --- |
| `workspace_id TEXT PRIMARY KEY` | `workspace/schema.py:17` |
| 由 `uuid4().hex` 生成，不接受客户端指定 | `workspace/store.py:40` |

→ **全局唯一由数据库约束保证**，不是 bug。本条到此为止，不再重复怀疑。

**前提失效条件**（写下来以免下次重新论证）：若将来允许客户端传入 `workspace_id`，或引入跨库/跨副本合并，唯一性不再由单个库的 PRIMARY KEY 保证，需重新核验。

## 4. P0-SEC-1：面板直读路径的越界与敏感访问核验（独立工作流）

**已知事实**：`check_path()` 仅被 `sandbox/tools.py` 调用（`:174`、`:209`、`:229`、`:978`，以及 `first_sensitive_entry` 内部的 `paths.py:128`）。`sandbox/http.py` 的面板直读路径**不调用**它——`http.py:86-87`（列目录）、`:112-113`（读内容）直接读本地磁盘。

**"没有调用 `check_path()`"不等于"已证明存在任意文件读取"。** 待核验五项（只读，不改代码）：

1. 面板各接口是否校验当前用户对该 workspace 的归属（`_existing` 里有 `workspace_path(..., current_workspace_id=...)`，但 `local_workspace_path` 走的是另一条路，覆盖范围未确认）
2. `local_root` 是否只能来自经过授权的绑定记录（`normalize_local_root(strict=True)` + DB 行）
3. 面板传入的相对路径是否可能穿越（`resolve_workspace_path` 有 `..` 与绝对段拒绝，但调用方是否都经过它未确认）
4. 列目录 / 读内容 / 图片预览 / 上传 是否使用同一套路径限制
5. junction / symlink 是否能让面板访问绑定根以外的文件（`Path.resolve()` 会跟随链接，需实测）

**明确不做**：不为了修这一项，把敏感路径策略塞进 P0-2 的路径映射改造。两者混在一起会让"路径一致性"和"访问控制"互相背锅。
