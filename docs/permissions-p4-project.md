# 权限 P4：项目级档位（覆盖，不是上限）

> 状态：已实现（2026-11-14）。取代 P3 的「三级作用域、全部只能收紧」。
> 相关：`permissions-p1.md`（能力声明）、`permissions-p2-approval.md`（审批挂起）、
> `archive/permissions-p3-scopes.md`（已废弃的设计）。

## 1. 问题

同一个用户在不同项目里需要不同的执行档位：个人文档仓库只想给它读，代码仓库要它
直接改；全局设一次不成立——设成只读，代码项目没法干活；设成完全，文档仓库随时可能
被改。

所以需要「项目级」这一层。

## 2. 语义：项目覆盖用户，快照只能收紧

```
scope  = workspace  if 项目设了值  else  user
effective = min(scope, ceiling)
```

三个来源，**两种关系**——把它们写成一条 min 链是错的：

| 关系 | 谁对谁 | 一句话理由 |
| --- | --- | --- |
| 覆盖 | `workspace` 顶替 `user` | 同一个人在两处设置，粒度细的那处更接近他此刻的意图 |
| 收紧 | `ceiling` 压住结果 | 授权快照是「过去某一刻允许到这里」，未来不能超过它 |

### 为什么项目级能放宽

OAuth 的 scope 只能缩，因为子层是**别人的应用**，扩权就是越权。这里的子层是
**同一个用户**为某个项目做的选择：全局设只读、给某个仓库设完全，表达的是
「这个仓库我知道在干什么」，不是第三方给自己发权限。

反过来（做成上限）的代价是具体的，不是理论上的：用户在这个项目里选了完全，
行为仍是只读，界面上没有任何地方能解释这件事。P3 就是这个形态，随后整体收回。

安全边界不靠这一层兜：

- 敏感路径在任何档位下都不可读写（`paths.py::check_path`，「完全」也拦）；
- 审批档的每次放行绑定到具体那一次调用（`agentrun/approval.py`）；
- **Agent 没有任何工具能改这两处设置**：只读/审批档下 `run_command` 被
  `EXEC` 能力拒绝，命令层没有执行能力；能改档位的只有用户点设置页。

### 覆盖的代价，以及为什么不藏起来

用户把全局从「完全」调成「只读」，已经显式设过的项目**不会**跟着变——它保留了
那次更具体的授权。这是覆盖语义的固有结果，刻意保留。

代价是「改全局」不等于「全盘收紧」。所以两个地方必须说实话：

1. 工作区设置里显示「当前：完全（覆盖用户设置）」，让用户看见这个项目没跟全局；
2. 本层不提供「全局一键覆盖所有项目」——真要收，去每个项目改一次。加一个隐式
   的全盘重置比留一个显式的例外更危险：用户不知道哪些项目被改了。

## 3. 为什么不是三级

会话级曾经一起做过（P3：用户 / 工作区 / 会话，三层全上限）。不做会话级，理由
与「多做一层更安全」相反：

- 会话是**临时容器**，一次对话结束就没了。档位跟着项目走才是稳定的边界：同一个
  项目下次打开还是那档，用户不需要每次确认「这次是不是被压着」；
- 三层之后，「哪一层在生效」需要用户在每个对话里对账一次。P3 的界面就是这个
  效果，用户看到的是两个开关，只有一个是真在起作用。

现在只有两级：用户级是默认值，项目级是显式例外。

## 4. 数据与接口

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 列 | `workspaces.permission_level TEXT NOT NULL DEFAULT ''` | 空 = 未设置。**独立列**，不塞 `metadata`：metadata 是整体替换的，会顺手把档位冲掉（= 放宽） |
| 存储 | `workspace/store.py::get_permission_level / set_permission_level` | 查不到行返回空串（未设置），不抛错 |
| HTTP | `PUT /internal/workspaces/{id}/permission-level` | `{"userId","permissionLevel"}`；空串 = 清除；非法值 400（不静默降级） |
| 响应 | `WorkspaceResponse.permissionLevel` | 列表与创建/重命名都带 |
| BFF | `PUT /api/permission-level` | body `{permissionLevel, workspaceId?}`：带 `workspaceId` 落到项目级，不带落到用户级。一条路由两个落点，同一件事不留两条前端通道 |
| HTTP | `PUT /internal/user-settings/permission-level` | 只改用户级这一列（body 只有 userId 与 permissionLevel）。不存在「整份设置回写」的路径：为了一个下拉去覆盖整份设置，等于给它顺手冲掉别的字段的机会 |
| 前端（聊天页） | 输入框工具栏，模型选择器左边 | 盾牌按钮显示当前生效档位，点开四选一（有工作区时多一项「跟随用户设置」）。这是项目级的唯一入口 |

**设置页里为什么没有「按项目覆盖」那一块**：曾经有过一段固定列表（每行一个工作区、
四选一下拉），理由是「打开设置就能看见每个项目是哪一档」。实际用起来它成了同一件事的
第三处入口：档位是「这一轮我要它多谨慎」的临场判断，判断发生的地方在对话里，不在设置里。
留着它只会多一种「我在这儿改过」和「它在别处被改」对不上账的可能，所以删掉了——项目级
本身还在，落点是聊天页那个盾牌。

### 聊天页那个盾牌按钮改的是哪一级

一个入口、两个落点，规则只有一条：**改这一轮对话实际会用的那一档**。

| 当前会话 | 落点 | 菜单底部文案 |
| --- | --- | --- |
| 绑定了工作区 | 该工作区的档位（覆盖全局） | 作用于工作区「米核」里的对话 |
| 没有工作区 | 全局档位 | 作用于所有对话与定时任务 |

菜单里必须写明落点：同一个下拉落在两个地方，不写清楚就会出现「我在这里点了
一下，为什么全局变了」。反过来，如果拆成两个入口（一个改项目、一个改全局），
用户在对话里就得先判断「我现在这档是谁定的」——那是把内部的解析顺序摊给用户。

为什么不把设置页当唯一入口：档位是「这一轮我要它多谨慎」的临场判断，和「选哪个
模型」同一类。要求用户为此打开设置、滚到第三块、关掉弹窗，他会干脆一直用完全档
——那才是真正的安全损失。

工具在跑的时候菜单是禁用的：档位在 run 开始时解析一次，中途改不会影响当前这一轮，
允许改就会出现「我改成只读了，它怎么还在写」。

解析入口仍是单一函数 `chain.resolve_effective_level(load_user, user_id,
load_workspace=..., workspace_id=..., ceiling=...)`，run 执行只调它一次；
`Resolution.binding` 取 `workspace` / `user` / `ceiling`，用来解释「这一档是谁定的」。

## 5. 取不到数：三种情况必须分开

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| 项目没设（空串） | 回落用户级 | 这是绝大多数情况，中性 |
| 工作区查不到（已被删） | 回落用户级 | 删掉一个项目不该把它变成一个永久的只读陷阱 |
| 读失败（DB 异常） | **按只读**，记 `Resolution.errors` | 当「没设置」处理等于「数据库抖一下就能提权」；让异常穿出去会让整轮 run 挂掉 |

`store` 对「查不到」返回空串、对「读失败」抛异常——这个区分是上表能成立的前提。

## 6. 边界（如实记录）

- **定时任务不读项目级**：cron 请求没有工作区上下文（`session_key = cron:{id}`），
  它按「用户级 + 创建时快照」执行。定时任务本身不绑定项目，所以不存在「这个项目的
  定时任务」这种对象；反过来说，给项目设了只读，也不影响任何定时任务。
- **项目档位只能在聊天页看「当前会话那一档」**：设置页已经没有「按项目覆盖」列表，
  想看某个项目是几档，要进到一个绑了该工作区的会话里读盾牌。工具被拒时错误文案已写明
  当前档位，但「进对话前先知道这个项目是几档」目前得先进去看一眼。
- **没有「一键把某个项目的设置同步为全局」**：见 §2 最后一段。

## 7. 守卫

`tests/test_permission_scopes.py`（18 例）盯的是四个不变量，不是功能清单：

1. 项目覆盖用户——**两个方向都测**（只测更严方向的话，min 也能通过）；
2. 没有工作区时回落用户级；
3. 快照对用户级与项目级都只能收紧；
4. 会话级不许复活（`session_meta` 不得有列，写入路由必须 404）。

第 4 条是防止「再加一层」：加回来只要一行代码，加回来之后三层各存一份档位、
谁也不报错，只有这条断言能挡住。
